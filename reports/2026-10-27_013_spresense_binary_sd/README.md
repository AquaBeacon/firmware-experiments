# Spresenseバイナリ保存とSD書込みタイムアウトの再確認

## 前提
- 2026-10-27 JST。ユーザーがSpresenseと親機を接続し、Spresenseのバイナリ保存とSD復旧不調・約4GB使用を相談。
- 親機USB A444A41EE9334705 / COM6のP_MAIN応答と、Spresense USB 10878C89E6DBED1197F5F12D62C613AC / COM7のIMU_LOG・LINK・pps_input=D02応答を照合。
- 書込みはSpresenseのみ、各書込み前にqのSTOPPED_REMOVE_SDを確認。親機・子機・元リポジトリ・SDKの変更なし。PC Wi-Fi切替、実機Web操作、SDフォーマット、既存ログ/校正の削除なし。
- ピン変更なし。親機GP6=外部GNSS PPS入力、J_SPR1.1–D02=PPS入力専用、GP7–D03=既存半二重。隣接AquaBeacon/pcb/build_parent_main.pyのコネクター定義と照合、旧設計の信号用途はユーザー指定が優先。親機温度/水圧/LCDは対象外。

## 調査・実測
- 親機/子機の通常ログはAQBIN001。Spresenseはschema3のCSVだった。
- Spresense SDはFAT32、総記録領域31925993472byte、初回空き27009728512byte。使用済み4916264960byte。空き領域があり、満杯による停止ではない。カードの物理健全性やファイルシステム全体の整合性を証明したものではない。
- 変更前CSVでWRITE/errno110（ETIMEDOUT）を再現。再試行で記録再開しても再発する。先行レポート012と同様の障害で、復旧回数増加だけを安定動作成功としない。
- 最初のバイナリ版でも同じ110が再発。保存量だけを減らしても解消しなかった。179件の状態を取得し、観測中SDエラー2→4、保存行数6336→17353、その後記録停止を確認。起動バナーが既に通過していたため初回観測スクリプト末尾の「新ファーム未観測」assertは失敗したが、生ログと状態JSONは保存済み。書込み自体のパッケージ検証は別に成功している。

## 実装
- Ixxxxx.BIN/Txxxxx.BIN、AQSBIN01版1、512byteヘッダー＋128byte固定レコード・各CRC32。IMU生/補正float32と温度・全時刻・品質・校正/PPS/親機参照を丸めず保持。親子のAQBIN001とは区別する。
- SubCore1は固定長符号化を使用、共有識別子IMU4で旧コアとの混在を拒否。両コアを更新。
- MainCore専用の32byte境界512byteバッファーへコピーしてからwrite。通常は32行4096byteをまとめ、停止時は端数も排出する。共有メモリ・アラインメント・頻繁な端数書込みという差を抑える対策であり、最下層のDMA/電源/カードの原因特定ではない。
- 既存512byte境界制限、EINTR/短いwrite/エラー処理、同期、Watchdog、再試行予算は維持。
- statfsの空き確認、旧CSV/BIN/検査名の衝突回避、O_EXCL、候補前進を実装。空き不足はENOSPCとし削除・フォーマットしない。
- 両ログを256MiB前に同期/閉鎖し、新規ペアへ分割。signed32bit off_tとFAT32の単一ファイル境界を予防する。分割中の取得キュー欠落は計数し、連続無欠落を保証しない。
- PCのBIN/旧CSV逐次読取り、CRC付きCSV変換、校正/時刻/連番検査、姿勢解析へ対応。通常は切れた末尾を失敗とし、明示オプションだけ完全レコードを回収して切捨てバイト数を返す。CRC不正は拒否。出力を上書きしない。

- Spresense両コアと指定PlatformIO parent/child100ビルド成功。
- 指定venvでscripts/test_host.py全体PASS。グローバルPythonにはziglangがないため、既存の指定venvを使用した。
- C++→Pythonで32サンプル/参考時刻を往復、全ディスクバイトの破損・版/予約領域/時刻不確かさ・末尾欠落・64bit時刻・連番wrap・CSV互換を検査。
- 実openLogs/rotateLogsIfNeededを模擬SDへ結合し、満杯・権限異常・既存名・CRCヘッダー・上書きなし・両ログ分割・同期失敗を検査。削除するのは当該試験が排他作成したV検査ファイルのみ。
- 実writeComplete/serviceFormatterを使用し、全512開始位置、専用バッファーの配置と内容、短い書込み/EINTR/停止、32行待機とSTOP端数排出を検査。
- 親機のBIN/CSVの姿勢解析・カメラ専用動作抽出の同等性と既存子機解析を確認。
- MainCore初回アップロードが90秒で期限切れ。今回起動した残存flash_writerだけを停止し、USB個体を再確認して再試行。パッケージ検証・保存・再起動を確認。初回を成功と数えない。

## 実機最終確認
- 専用バッファー＋32行まとめ版のMainCore書込みはパッケージ検証・保存・再起動まで成功。SubCore1との識別子は一致。
- 同版でもWRITE/110が再発。観測の最初から過去エラー1件があり、約11.4秒の窓でSDエラー1→2、保存行数19942→30410、キュー廃棄298→574。根本障害の解消・安定保存を合格としない。最大120秒の観測は再発時点で打ち切った。
- 安全停止後に校正ファイルをUSB cで読取り、K00001.CAL/K00003.CALをPCに保管。いずれも形式/CRC有効。適用番号3と有効状態を保持。
- 新規の短い記録を作成したが、その途中にもWRITE/110が発生したため停止。USB i/gでそのペアを読戻した。IMUファイル90112byte＝512byteヘッダー＋700×128byte。700件全てのCRC・連番（欠落0）・校正番号/補正数値・時刻品質条件が検証成功。破損末尾の許容オプションは使っていない。これは回収できた700件の整合性であり、取得全サンプルの無欠落保存ではない。
- 参考時刻ファイルはヘッダーのみでデータ0件。実機の参考時刻レコード内容は未検証、C++/Pythonの模擬データ往復のみ検証。
- 最終親機USBでSpresense link_fresh=true / imu_ok=true / recording=false / sd_state=STOPPED、WRITE/110履歴、校正番号3適用・保存/復元エラー0を確認。親機自身はsd_reason=NONE。SpresenseのPPS入力は届くがUTC対応は未成立。姿勢収録・測距を開始していない。
- **結論：バイナリ保存と実データの整合性は確認したが、SD復旧不調は未解決。記録は停止してあり、別の既存FAT32カード・接点・給電を比較するためのユーザー作業待ち。フォーマットや既存ログ削除では対処していない。**

- 実カード満杯、256MiB境界、数時間以上の保存、物理抜去/電源断、実機Web。実機の同期/距離/姿勢の絶対精度は合格としていない。
