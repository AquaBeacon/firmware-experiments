# 親機収録8のSpresense IMU解析（2026-10-28）

## 前提
- 親機SDで回収済みのP_MAIN_BODY_CAPTURE_00008.binについて、ユーザーがSpresense側SDを挿入。
- D:はラベル「ボリューム」、FAT32、約32GB。親機SDから切り替わったことを容量・ファイル構成で確認。
- 前回の[親機収録確認](../2026-10-28_005_parent_body_check/README.md)で保留していた加速度・ジャイロを検査する。磁気は前回と同じ親機側ログを用いる。
- SDの書込み/削除/フォーマット、USB操作、ファーム書込み、Wi-Fi切替、実機Web操作なし。

## 実施
- Iログ7件のヘッダーと先頭/末尾のサンプルを確認し、収録8の親機boot=3385016482を含むI00005.BINを選定。収録中のparent_session、個別校正3番、GNSS/PPS対応UTC窓で照合。
- I00005.BIN、T00005.BIN、K00001〜00003.CALをPCのreports/raw/2026-10-28_006_parent_imu_alignmentへコピーし、5件全てのSHA256をSD原本と照合。一致。
- 既存verify_spresense_logで選定IMUログ全件のCRC・連番・時刻条件・生値/補正値・校正係数による補正計算を検査。
- 既存body_alignmentと同じ区間条件（開始後1秒〜終了前0.25秒、対象起動と校正番号一致、time_quality=2）で静止統計と4姿勢の角度整合を算出。
- 既存body_alignmentによる通常の全軸解析も実行し、停止理由を確認。別途、既存--movement-onlyで動作区間のCSVをPC側に抽出。

## 実測：ログと個別補正
- I00005.BINはAQSBIN01、全1,661,440サンプルのCRCエラー0、保存seq欠落0、補正計算一致1,661,440件。既存検査の受信順・sample時刻・UTC品質・未測定時刻不確かさ条件も通過。
- K00001/00002/00003.CALは全て既存係数検査を通過。今回の収録は3番を使用し、enabled=true。
- I00005には親機再起動前後の複数sessionがある。今回のsessionは1,088,040件で、そのうちtime_quality=2が599,229件、time_quality=1が488,811件。収録外も含む全sessionの件数であり、今回の区間全体を未同期だったと解釈しない。
- T00005.BINは520レコードを全件読取り、CRC/末尾正常。今回sessionの診断ではimu_errors/imu_gaps/sd_errorsは0を維持。

## 区間内の時刻品質
- 解析に採用したsample_utc_usは各区間で単調、10msを超える間隔なし。
- 区間1/3/5で採用seqに各1件の飛びがある。元ファイル全件のseqは連続しており、該当seq=1680630 / 1714464 / 1840126を再読取りしたところ、いずれも保存されていてtime_quality=1、sample_utc_us=0だった。解析時のUTC品質フィルターによる除外で、保存レコードの欠損ではない。
- この瞬間のUTC品質低下の原因は未確定。ログ全体にわたるUTCの完全連続や絶対同期精度を認定しない。

## 最終判定
- **加速度・ジャイロの静止/4姿勢整合：通過。ログの保存・補正計算：検査通過。**
- **磁気を含む機体軸合わせ全体：不合格・未保存。** 通常の既存解析はIMU条件とimu_fitを通過した後、magnetic_fitの「Magnetic field magnitude inconsistent」で停止した。
- 磁気の平均ノルムは前回と同じ66.73 / 62.28 / 78.38 / 85.78µTで、現行の磁場整合条件を超える。環境・取付/搭載物・通電状態・個別磁気補正の影響の切り分けが残る。
- 規定を緩めたり磁気を省略して合格扱いにしたりしていない。インポート用parent_axes.jsonは生成されず、SD保存・実機への適用も行っていない。
- 既存4姿勢からのIMU回転行列はdiagnostic.jsonに診断値として保持し、全軸のインポート形式とは区別した。
