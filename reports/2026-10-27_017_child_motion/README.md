# 子機の区間5「IMU更新待ち」の調査

## 前提
- ユーザー報告：子機の機体軸合わせで区間5が「IMU更新待ち」のまま。機体の状態ではIMU取得中。
- PCのWi-Fi切替、実機Web操作、ファーム書込み、記録停止・再開、SD変更は行わない。

## 実施
- 子機のBNOイベント取得、通常サンプルキュー、SD処理、bodyObserveMotion、Motion判定、Web表示の経路を確認。
- USB一覧の親機シリアルA444A41EE9334705 / COM6と、受信P_MAIN応答を照合し、約4秒間の定期状態を読み取り。
- 子機USB A521D21EB1DCFB44は一覧に存在せず。子機のBODY_STATUSをUSBで直接照会できない。
- コード・仕様の変更なし。ビルド・ホストテストは未実施。

## 実測
- 親機経由の子機情報：link_age_ms=101、imu_age_us=2723、imu_samples=200236、sd_errors=0、rows=33030、durable_rows=32978、dropped=230924（累積）。
- 累積droppedの発生時期・内訳・今回の症状との因果は未確認。
- 親機のbody_calibrationは親機自身の値であり、子機の区間状態として扱わない。

## コードから確認したこと
- 機体のIMU状態はセンサー取得の新鮮さで判定する。
- 区間5の更新は、通常サンプルをSD処理で取り出し、freshのジャイロbitが立っていて有限値の場合にMotionへ通知する別経路。
- 最初の3秒は更新判定から除外し、最新の受理更新が5秒以上古い場合も「IMU更新待ち」になる。両表示の食い違いだけでセンサー故障や動かし方不足とは断定できない。

## 未検証・次の確認

- 区間5中の更新、サンプル消費、最新ジャイロ値、キュー遅延とWeb表示を切り分ける。根本原因は未確定。

## 続報：子機USB識別と判定経路の修正
- ユーザーの接続後、子機USB A521D21EB1DCFB44 / COM3とC_MAIN定期応答を照合。
- 書込み前の子機bodyはa=0/m=15/z=3（区間1〜4記録済み、収録中止）、d=7（3軸の動きの検出履歴）、q=0。現在のIMU取得は継続していた。中止後のq=0だけでは、区間5中に停止した直接原因を確定できない。
- 観測中も通常ログの保存と取りこぼしが増加。詳細な差分はrawのsummary.json。SDキューの実遅延時間そのものは計測していない。
- コード上、区間5の更新がSDキューの消費時にだけ通知され、取得時刻が古いと新鮮さ5秒未満の条件を満たさない問題経路を確認。実際の今回の失敗原因はこの経路が有力だが、区間5中の再現観測前に確定としない。
- BNOジャイロの最新値・単調取得時刻・更新番号をmutex保護で渡し、core 0のbodyTickで受け取るよう修正。SDキューからの通知を削除。通常ログ・取得時刻・廃棄カウンターを保持。
- 実bodyTickを用いた試験で、SDキューを消費しない状態でも更新/動作/30秒条件が成立し、同一更新の再読取り・5秒の失効・非有限値・区間外の更新は合格扱いにしないことを確認。
- システムpythonではziglang未導入で実行不可。既存P_MAIN_experimentのvenvからscripts/test_host.py全体PASS。parent/child100ビルドSUCCESS。
- scripts/flash.py child100でUSB番号とC_MAIN応答を再照合、安全停止完了後に子機だけ書込み。Flash全量照合OK。親機/Spresenseの書込み、Wi-Fi切替、SDフォーマット/削除は行っていない。
- 更新後はBNO校正保存履歴b=3、軸未保存g=0、body開始不足x=0を確認。これはBNO内部係数の読出し一致確認ではない。新規C_MAIN_IMU_100Hz_35415.binへ保存し、IMU欠落カウンター0/SDエラー0。ただし保存の廃棄は継続。
