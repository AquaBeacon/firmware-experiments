# 親機SDカード全ファイル保存検査（2026-10-28）

## 前提
- ユーザー依頼：親機のSDカードを挿入したので保存がうまくいっているか確認する。
- 対象D:はFAT32のリムーバブル媒体。前の子機カードと容量・内容が異なる。親機AQBINのrole=1、BODY_CAPTUREの機体ID A444A41EE9334705を確認。
- 親機関連696件とWindows管理2件の計698ファイル、5,287,134,013byteを全件読取り。
- SD書込み・修復・削除・フォーマットなし。USB操作・ファーム書込み・Wi-Fi切替・実機Web操作なし。温度/水圧/LCDは検証対象外。

## 実施
- 再帰列挙した全ファイルを読取り、SHA256と形式別検査結果をPCのreports/raw/2026-10-28_002_parent_sd_full_checkへ保存。列挙/読取り失敗0、検査中のサイズ・更新日時変化0。
- AQBIN 202件：ヘッダーと全1,345,042レコードのCRC、形式、末尾、種類別単調時刻を検査。HEALTHの累積エラーと磁気観測の有限値も確認。
- Spresenseの旧CSV 114件（IMU Ixxxxx.CSV 57件＋参照Gxxxxx.CSV 57件）：全41,397,074行のCRC、列構造、数値、センサー値、seq/受信時刻を検査。全IMU CSVは個別校正列・PPS対応時刻列を持たない旧形式。
- GNSS UBX 91件：全596,128フレームの長さとチェックサム、RAWXの構造・観測間隔を検査。
- RTCM3 88件：全48,203フレームの長さとCRC24Qを検査。CRC24Qはリポジトリcommon/gnss_binary.hと同じ多項式を使用。
- GNSS状態JSONL 88件：全35,563行のJSON構造、必要キー、時刻、保存件数・取りこぼしカウンターを確認。JSONL自体にCRCはない。
- 校正セット3件、磁気校正1件、測距校正7件、NTRIP設定2件：各独立レコードのサイズ・CRC・バージョンと各形式の値範囲を検査。測距の対応周波数をcommon/acquisition.hと再照合。設定の接続先・認証情報は出力しない。
- Vxxxxx.BIN 100件：各512byteの起動時読書き試験パターンを全byte確認。
- Windows管理ファイル2件：全byteの読取りとハッシュのみ。

- 校正・設定レコード13件とVファイル100件は全て検査通過。
- 親機TIME_POSITION/HEALTHの100組は全て存在し起動session一致。Spresense I/Gの57組も全て存在。
- GNSS状態JSONLの88組は対応UBX/RTCMが存在。最終状態行のRAWX/SFRBX保存済み件数が、実UBXの該当フレーム件数を上回る例は0。

## 実測：SDエラー・計測欠落の履歴

CRCが正しいことと、取得・保存の取りこぼしがないことを分ける。下記には累積履歴を含み、重複を除いた注記対象は78ファイル。78件のファイル破損ではない。

### 親機本体
- HEALTH 100件のうち8件に累積sd_errorsがある。当該ログの先頭と末尾で同値であり、ログ内の増加は0。

| HEALTHの番号 | 最初/最後のsd_errors |

| 00019 | 1 / 1 |
| 00020 | 2 / 2 |

- 検査した親機HEALTHのdropped/imu_gapsは非ゼロなし。ただし親機自身の値であり、別機器Spresenseの無欠落を意味しない。
- 周期HEALTHの最終rows/durable_rowsは、最後のclose時点の保存件数とは限らない。最終件数との完全一致をこの検査だけで認定しない。

### カード上に残る過去のSpresense CSV
- IMU CSV 57件で、ファイル内seqの欠落/逆行・受信時刻逆行・非有限IMU値を検出しなかった。
- G参照CSV 57件のうち54件に累積imu_gapsとsd_errors、1件に累積imu_errorsの履歴がある。いずれのカウンターも各ファイル内で最初から最後まで増加なし。
- 例：G00056.CSVはimu_gaps=30,931、sd_errors=78を維持。旧ログの保存行seqが連続でも、上流取得の欠落履歴がないとは言えない。
- このカードには現在のSpresense個別校正3番のSCALレコード/現在の形式のPPS対応IMUログがない。旧I/Gログが存在することを、現在のSpresense本体SDの保存品質確認の代わりにはしない。現在のSpresense記録・補正計算・PPS対応の完全検証には同機のSDが別途必要。

### GNSS・補正データ
- RAWX 177,099フレーム、SFRBX 211,289フレーム等を確認。フレームの存在とCRC整合はPPK解析や位置精度の合格ではない。
- GNSS JSONL 4件で当該収録のdroppedが増加：00046は0→2、00047は0→147、00048は0→9、00049は0→60。
- 補正データのログ取りこぼし履歴は00047/00048/00049の3件。rtcm_log_droppedはそれぞれ0→18、18→195、195→396。この値は累積のためファイル間で単純加算しない。
- 保存済みRTCMフレームは全CRC整合だが、保存前に落ちた補正フレームは復元できない。
- RAWXの1Hz想定ゲート（0.5〜1.5秒）外の間隔を10ファイルで検出。うち8ファイルはGNSS週0との切替を含み、巨大な秒差をそのまま欠落時間として数えない。00046.ubxと00049.ubxは週2442内で2秒間隔が各1回あり、1Hzの観測が1周期飛んだ状態。受信機出力か保存経路のどこで落ちたかはファイルだけでは確定しない。
- 例として46952の収録は、状態ログ内のdropped/RAWX・SFRBX・その他のenqueue_dropped/UBXエラー/UARTオーバーフロー全て0を維持。番号の大小を収録時系列とは扱わない。

## 校正・姿勢収録
- 親機校正セット1番はIMU=0/磁気=0、2番はIMU=0/磁気=1の下書き参照。3番はIMU=3/磁気=1。保存形式は全て正常だが、下書きを個別校正完了とは扱わない。
- 磁気校正1番は有効。測距校正は世代1〜7を保存し、最大世代7はenabled=true・200kHz・pattern=1・28点。ファイル値の検査であり、距離精度の実測認定ではない。
- NTRIP設定はA世代3/B世代4が両方CRC正常。秘密情報は確認結果に含めない。
- BODY_CAPTURE_00001/00002はどちらも開始イベント1→中止イベント5、mask=0。区間開始や全区間完了はない。参照TIME_POSITION/HEALTHは存在しsessionも一致、校正参照はIMU=3/磁気=1。
- 親機のBODY_ALIGNはカード上にない。今回のカード内容から、親機の機体軸合わせ完了とは判定しない。

## 判定
- 現在見える全ファイルは読取り可能で、検査したCRC/チェックサム付き保存データの破損・末尾欠損は検出されなかった。
- ただし、過去のSpresense診断には取得欠落・SDエラーの履歴、GNSSの一部収録には保存取りこぼし・観測時刻の不連続がある。親機の全記録を無欠落とはしない。
- 現在の記録動作の確認や原因修正は実施していない。今回の依頼は回収SDの読取り検査として完了。

## 未検証・限界
- 別のSpresense本体SD、現行校正係数との補正値一致、親機とSpresenseのPPS/UTC対応、実機上の再起動復元。
- 未割当領域を含む物理全セクター、FAT割当の完全性、実書込み・容量偽装試験、将来の長時間/同時負荷。chkdskや修復は今回実施していない。
- RAM中の未保存末尾が正常レコード境界で失われた場合は、ファイルだけでは検出できない。JSONLは構文検査でありCRCによる完全性保証ではない。
- GNSS週0を含む区間、取りこぼしを含む区間をそのまま後処理の時刻基準に使用しない。PPKには同時刻の基準局観測等が必要で、今回PPK解析はしていない。
- 温度/水圧/LCDの機能、姿勢/時刻/距離/位置の絶対精度は未検証・未測定。ビルド/ホストテストはファーム変更なしのため実施していない。
